# Сценарий в ИС, П1 «Модель v2»: координация исполнения

Статус: готов к запуску, 2026-10-16.

Что исполняется: [PLAN_sim_v2_model.md](PLAN_sim_v2_model.md), задачи 0–15. Код в плане полный, поэтому исполнителю не
нужно исследовать кодовую базу — только перенести код, прогнать тесты и доложить.

## 1. Роли

| Роль | Кто | Что делает |
| --- | --- | --- |
| Владелец | Человек | Создаёт и запускает сессии исполнителей по готовым заданиям раздела 5, передаёт координатору их доклады |
| Координатор | Отдельная сессия, Opus | Готовит worktree волны, принимает доклады, сливает ветки в `sim-editor`, ведёт таблицу состояния (раздел 6), решает, можно ли начинать следующую волну |
| Исполнитель | Новая сессия на каждое задание | Выполняет свои задачи плана в своём worktree и докладывает по форме раздела 4 |

## 2. Правила экономии контекста

- **Каждое задание — новая сессия.** Исполнитель не продолжает чужой разговор и не получает истории: всё нужное лежит в
  плане и в тексте задания. Одна сессия — одно задание, после доклада сессия закрывается.
- **Координатор начинается с чистого листа.** Сессия, где шло обсуждение требований, координатором не становится: её
  контекст забит обсуждением. Новая сессия координатора читает только этот файл и, при необходимости, отдельные
  задачи плана. Между волнами координатор делает `/compact`, если контекст перевалил за половину.
- **Исполнитель не исследует.** Он читает свои задачи плана и только те файлы, которые правит. Поиск по коду — только
  командами, которые указаны в плане.
- **Доклады короткие.** Не больше 15 строк по форме раздела 4. Диффы, логи тестов и куски кода в доклад не входят.
- **Координатор не читает диффы целиком.** Он сверяет `git log --oneline` и `git diff --stat` ветки с картой файлов
  плана и прогоняет тесты, которые назвал исполнитель. Код читает только при расхождении.

## 3. Волны и модели

Задачи плана разложены по волнам по зависимостям. Внутри волны задания идут параллельно, каждое в своём worktree: их
файлы не пересекаются.

```text
Волна 0   [З0-4]                                   основа: копия v1, контракт, перевод, вид, стоимость
Волна 1   [З5-6 движок] [З7 оптимум] [З14а схемы]  после слияния волны 0
Волна 2   [З8-9 маршруты, оси] [З11 плеер]          после слияния волны 1
Волна 3   [З10 проверки] [З12 сервер] [З13 клиент]  после слияния волны 2; сливаются в порядке З10, З12, З13
Волна 4   [З14б пример, З15 проверка]               после слияния волны 3
```

| Задание | Задачи плана | Модель | Почему эта модель |
| --- | --- | --- | --- |
| В0 | 0, 1, 2, 3, 4 | Sonnet | Перенос готового кода из плана и точечные тесты; рассуждать почти не о чем |
| В1-движок | 5, 6 | Sonnet | Правки по месту в `engine.ts`, `protocol-codec.ts`, `replay.ts`, код дан |
| В1-оптимум | 7 | Sonnet | Новый модуль целиком из плана. Если тест упрётся в логику поиска — стоп и доклад, не переписывать алгоритм |
| В1-схемы | 14а: шаги 3–7 задачи 14 | Sonnet | Схемы JSON и тексты формата: нужна сверка с контрактом один к одному |
| В2-маршруты | 8, 9 | Sonnet | Два новых модуля целиком из плана |
| В2-плеер | 11 | Haiku | Механические замены по указанным строкам; ошибки покажет `tsc` |
| В3-проверки | 10 | Opus | Самая рискованная задача: переписывается `validate.ts`, прежние тексты ошибок обязаны совпасть, новые предупреждения на примере надо отличить от дефекта |
| В3-сервер | 12 | Sonnet | Много мест чтения сценария, часть находится поиском |
| В3-клиент | 13 | Haiku | Две правки по месту и доводка по `tsc` |
| В4 | 14б: шаги 1–2 задачи 14; 15 | Sonnet | Перевод примера скриптом и сводная проверка; полный прогон — только с разрешения владельца |

Fable не используется: в задачах нет ничего, что окупило бы самую дорогую модель. Если задание Sonnet или Haiku
остановилось на непредвиденном, координатор перезапускает его на модели на ступень выше с докладом прошлой попытки в
задании, а не продолжает ту же сессию.

## 4. Форма доклада исполнителя

```text
Задание: <код>, ветка <ветка>, коммиты <первый>..<последний>
Сделано: задачи <номера>
Тесты: <команда> — <PASS/FAIL, число>
tsc: <0 ошибок | список файлов с ошибками, если они ожидаемы по плану>
Отступления от плана: <нет | что и почему>
Стоп: <нет | что помешало и что нужно решить>
```

## 5. Задания

### 5.1. Общая часть каждого задания

Владелец вставляет её перед текстом конкретного задания.

```text
Ты исполнитель одного задания трека «Сценарий в ИС», П1 «Модель v2».
Работаешь ТОЛЬКО в worktree <WORKTREE>, ветка <BRANCH>. Все команды — из его корня.
План: docs/plans/PLAN_sim_v2_model.md. Сначала прочитай его вводную часть до «Задача 0» и раздел «Правила работы»,
затем — только свои задачи. Код в плане полный: переноси его, не исследуй кодовую базу сверх файлов, которые правишь.
Правила:
- тесты только точечные, `npm test -- <пути>`; полный `npm test`, `npm run test:cov` и `npm run dev` не запускать;
- типы: `npx tsc --noEmit --incremental false`;
- новых зависимостей не ставить;
- коммиты по шагам плана, без трейлера Co-Authored-By;
- если код плана не проходит тест и для починки нужно менять замысел (формулу, текст ошибки, контракт), остановись и
  доложи, не придумывай своё;
- в конце — доклад строго по форме из docs/plans/COORD_sim_v2_model.md, раздел 4, не длиннее 15 строк.
```

## 6. Работа координатора

### 6.1. Перед волной

Создать worktree каждого задания волны от текущей вершины `sim-editor`, подключить `node_modules` и `.env`:

```powershell
$name = "tb-sim-w1-engine"; $branch = "sim-w1-engine"
git -C C:\Repositories\test-builder-sim-editor worktree add "C:\Repositories\$name" -b $branch sim-editor
New-Item -ItemType Junction -Path "C:\Repositories\$name\node_modules" -Target "C:\Repositories\test-builder\node_modules" | Out-Null
Copy-Item C:\Repositories\test-builder\.env "C:\Repositories\$name\.env"
```

Затем сообщить владельцу: какие задания запускать, на какой модели, с какими подстановками `<WORKTREE>`, `<BRANCH>`.

### 6.2. После доклада

1. `git -C <worktree> log --oneline sim-editor..HEAD` и `git -C <worktree> diff --stat sim-editor...HEAD` — коммиты и
   файлы совпадают с картой файлов плана для этих задач.
2. Прогнать тесты, которые назвал исполнитель, в его worktree.
3. Влить в `sim-editor`: `git -C C:\Repositories\test-builder-sim-editor merge --no-ff <branch>`.
4. После слияния всей волны — `npx tsc --noEmit --incremental false` и точечные тесты всех задач волны в
   `test-builder-sim-editor`.
5. Удалить worktree задания, СНАЧАЛА сняв junction, иначе удаление вынесет `node_modules` главной копии:

```powershell
Remove-Item "C:\Repositories\$name\node_modules" -Force
git -C C:\Repositories\test-builder-sim-editor worktree remove "C:\Repositories\$name"
git -C C:\Repositories\test-builder-sim-editor branch -d $branch
```

И последним шагом — обновить таблицу 6.3.

### 6.4. Ожидаемо красное между волнами

Контракт v2 (задача 1) меняется раньше потребителей, поэтому до своих задач часть проверок красная. Это не дефект волны.

| Что | Почему | Зеленеет после |
| --- | --- | --- |
| `tsc`: ошибки в `shared/sim/*`, `server/**`, `client/**` | Потребители читают поля v1 | В1–В3 по мере слияния; ноль ошибок — после В3 |
| `tests/sim-validate.test.ts`, `tests/sim-scenario-archive.test.ts` | Прежний `validate.ts` ждёт `version: 2` и не знает v1 | В3-проверки |
| `tests/sim-engine.test.ts`, ожидание версии результата | Версия результата уже 2 | В1-движок |

Всё остальное красное после слияния — дефект: доложить владельцу. Откатывать слияние без его согласия нельзя.

### 6.5. Когда останавливаться

- Исполнитель доложил «Стоп» — координатор решает сам, только если решение есть в плане или в
  [v2-design.md](../specs/sim-scenario/v2-design.md). Иначе — вопрос владельцу, по одному.
- Конфликт слияния в файле, который по плану трогает одно задание, — признак ошибки исполнителя: ветку не вливать,
  перезапустить задание.
- Полный `npm test` — только после явного «да» владельца, в конце волны 4.
